### TTS 配置保存异常（AI播报 Tab，MiMo 选中 → "须选择 TTS 平台（百炼）"）
结论：**确认存在 Bug**——后端 `_normalize_tts_provider()` 把 MiMo 归一为空串，但保存校验 `not provider and model_id` 把"空 provider + MiMo model_id"当成了"未选平台 + 自定义 model"。

调用链（仅记录，未改代码）：
1. UI：保存 → `web/static/modules/settings.js:638 window.saveDanmuReadSettings()`
2. Front：`web/static/app.js:863-877` → 收集 `provider=provider?.wire_id|provider?.id` 与 `model_id=model?.id` → `PUT /api/danmu-read/config`，payload 含 `provider="mimo"`、`model_id="mimo-v2.5-tts"`
3. Route：`app/web_api/danmu_read_routes.py:78-85 put_danmu_read_config` → `normalize_put_payload` → `save_config` → `invoke_main(read_api.save_config, bridge.danmu_app, payload)` → `app.apply_danmu_read_config`
4. Service：`app/main_mic_mixin.py:359 apply_danmu_read_config` → `DanmuReadService.apply_config`
5. Bug 落点：`app/danmu_read_service.py:301 _normalize_tts_provider("mimo")` 返回 `""`；`:316-326` 进入 `elif not provider and model_id:` 分支，抛 `tr("danmuRead.providerRequired")` = "须选择 TTS 平台（百炼）"。

根因：`app/danmu_read_service.py:83-91 _normalize_tts_provider` 将 `("","mimo",TTS_PROVIDER_MIMO)` 都映射成 `""`（设计：MiMo = 默认/隐式），但 `:316-326` 的保存校验沿用旧的"空 provider + model_id"含义去拒绝，没有把 MiMo 当合法组合。`validate_custom_tts_fields` 也只在非空 canonical provider 时校验，故 MiMo 链路被绕过了真实校验。

修复建议（仅方向，不在本轮动手）：
- 选项 A（推荐，行为最少）：保留 `tts_provider=""` 表示 MiMo 的存储约定，把校验条件改成"`not provider and not in {MiMo aliases} and model_id`"——即只有真正未指定平台时才报 `providerRequired`。
- 选项 B：保存端将 MiMo 写为显式 `"mimo"`（与 `config_defaults.DEFAULT_TTS_PROVIDER` 一致），`_normalize_tts_provider` 不再归一为空；读取侧照旧通过 `TTS_SECRET_PROVIDER_ALIASES[""]="mimo"` 把空值视为 MiMo（保持兼容）。
- 选项 C：放宽校验文案 + 不抛错，把 MiMo+模型走 `else` 分支补 `validate_custom_tts_fields`。

排查期间未写代码，未跑测试；建议在选定方案后跑 `tests/test_danmu_read_api.py` + `tests/test_danmu_read_service.py` 验证。
