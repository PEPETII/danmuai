# Live2D 正式接入 DanmuAI 计划（门禁后草案）

> 本文是第二阶段规划，不是当前授权。  
> 前置条件：`W-LIVE2D-SCREEN-POC-PLAN-001` 的完整报告结论为“通过”。

## 1. 进入条件

正式接入前必须同时满足：

- POC 验收清单全部通过；
- Windows 实机报告包含普通窗口、无边框游戏、焦点、穿透、透明和 30 分钟运行证据；
- 已确认渲染 SDK 的许可允许目标分发方式，模型资源的许可允许目标使用；
- 已决定模型资源的用户导入/本地路径策略，且不把 BOOTH 测试模型作为产品内置资源；
- 负责人新建并登记独立正式集成工单，写明允许区、禁止区、回滚和测试；
- 现有 `app/pet/` 的架构边界、线程模型和生命周期影响已由维护者复核。

任何一项缺失，都只能继续完善 POC，不能开始改正式代码。

## 2. 建议拆分的后续工单

### 2.1 渲染宿主与生命周期

研究如何在现有 `app/pet/` 边界内承载 Live2D，而不改变现有序列帧桌宠的默认行为。需要明确窗口创建、主线程归属、启动失败降级、停止/退出清理和单实例行为。

### 2.2 资源与许可

设计用户本地模型目录、路径校验、错误提示、资源版本和许可声明。不得把测试模型、SDK 私有资源或业务模型名称写入默认配置。

### 2.3 控制契约

在单独工单中定义动作、表情、缩放、透明度、拖动和鼠标穿透的最小公开契约。契约应使用稳定的用户/资源标识，不把某个模型的具体动作名当作全局业务语义。

### 2.4 Web/设置入口

仅在上述工单通过后，再评估设置页或控制 API。必须遵守现有 Web API、Qt 主线程和 UI 设计系统边界；不能由 HTTP 线程直接写 Qt 对象。

### 2.5 回归与发布

增加与实际改动范围匹配的定向测试，另做 Windows 实机矩阵、资源缺失矩阵、启停/更新/卸载影响评估。正式模型和许可证材料不得随测试夹具进入公开仓库。

## 3. 正式接入时必须回答的问题

- Live2D 窗口与现有序列帧桌宠是互斥、并存还是可切换？默认行为是否保持不变？
- Live2D 渲染是否要求额外原生 DLL、GPU 能力或打包 hidden import？
- 模型加载和渲染是否始终在 Qt 主线程，耗时资源解析如何避免阻塞启动？
- 透明窗口、置顶、穿透和游戏兼容性是否与现有 Overlay 窗口标志冲突？
- 动作/表情控制由何处发起，如何避免引入新的平行调度器或线程边界问题？
- 用户卸载或删除模型后，配置如何失效、恢复和清理？
- SDK 与模型授权是否覆盖源码分发、打包分发和商业使用？

## 4. 非目标重申

正式接入也不自动包含摄像头面捕、OpenSeeFace、MediaPipe、真人捕捉、虚拟主播功能或 AI 调度重构。若未来需要，必须另行立项。

## 5. 失败时的退出路线

如果 POC 或正式集成发现原生透明窗口、许可证、性能或游戏兼容性无法满足要求，应保留完整失败报告，删除/停用实验或集成功能，并不得用浏览器窗口伪装满足“桌面原生显示”门禁。
