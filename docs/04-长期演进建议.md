## 4.1 依赖注入容器化

### 现状分析

当前 `DanmuApp` 既是应用入口又是服务定位器（Service Locator）：
- `__init__`（`main.py:129` → `main_lifecycle_mixin.py:47-300`）直接 new 出所有服务：`ConfigStore`、`PersonaManager`、`DanmuEngine`、`AiWorker`、`RequestScheduler`、`MicService` 等 50+ 字段
- 8 个 mixin 通过 `self.*` 访问这些字段，无显式接口契约
- 测试必须用 `DanmuApp.__new__(DanmuApp)` + `bind_minimal_danmu_app(app, **overrides)` 绕过 `__init__`
- `app/application/` 子包虽是边界收口层，但仍通过 `app` 实例 getattr 访问字段

### 目标状态

引入显式依赖注入容器，将服务构造与使用分离：

```python
# app/container.py（新建）
from __future__ import annotations
from typing import Protocol

class ConfigStoreProtocol(Protocol):
    def get(self, key: str, default=None): ...
    def set(self, key: str, value): ...

class Container:
    """依赖注入容器。
    
    集中管理所有服务的构造与生命周期，
    DanmuApp 持有 Container 引用，各 mixin 通过 Container 获取服务。
    """
    def __init__(self, config_store: ConfigStoreProtocol, ...):
        self._config_store = config_store
        self._engine = DanmuEngine(...)
        self._ai_worker = AiWorker(...)
        # ...
    
    @property
    def config_store(self) -> ConfigStoreProtocol:
        return self._config_store
    
    @property
    def engine(self) -> "DanmuEngine":
        return self._engine
```

### 演进路径

1. **Phase 1：抽取服务接口**（低风险）
   - 为 `ConfigStore`、`DanmuEngine`、`AiWorker` 定义 Protocol 接口
   - 现有类实现 Protocol，无需改名
   - 测试可用 Fake 实现替换

2. **Phase 2：引入 Container**（中风险）
   - 新建 `app/container.py`，将 `main_lifecycle_mixin.py:_init_core_subsystems` 的服务构造逻辑迁移到 `Container.__init__`
   - `DanmuApp.__init__` 改为 `self._container = Container(...)`
   - mixin 通过 `self._container.config_store` 访问，保持 `self.config` 等别名向后兼容

3. **Phase 3：测试用 Container 注入**（低风险）
   - `bind_minimal_danmu_app` 改为构造 Fake Container
   - 单测可直接 `Container(config_store=FakeConfig(), engine=FakeEngine())`

### 风险提示

- Qt 对象（QTimer、QThreadPool）无法简单注入（依赖 QApplication），需保持主线程构造
- 迁移过程中需保证 `self.config` / `self.engine` 等别名仍可用（向后兼容）
- 50+ 字段迁移需分批进行，每批验证测试通过

### 预期收益

- **可测试性**：单测可直接注入 Fake 服务，无需 `DanmuApp.__new__` hack
- **可扩展性**：新增服务只需在 Container 注册，不需触达 mixin
- **可维护性**：服务构造集中，依赖关系显式化

## 4.2 主链路事件驱动化

### 现状分析

当前主链路是同步调用链：
```
screenshot_timer → _on_normal_capture_tick → _schedule_capture → CaptureRunnable → _on_capture_completed → _trigger_api_call → AiRunnable → _on_ai_reply → _consume_reply_queue
```

- 每个环节直接调用下一个环节的方法，耦合度高
- `_consume_reply_queue` 已委托 `app/application/generation_pipeline.py:GenerationPipeline.consume_reply_queue`（W-GENPIPELINE-EXTRACT 已完成）；原 main.py 内 277 行分发逻辑已迁出
- 新增分发通道需修改 `_consume_reply_queue` 方法体
- 麦克风回复走 `_handle_mic_ai_reply`（`main_mic_mixin.py`），与视觉回复路径分离但逻辑相似

### 目标状态

引入事件总线（Event Bus），将主链路解耦为独立消费者：

```python
# app/events.py（新建）
from __future__ import annotations
from collections import defaultdict
from typing import Callable, Any


class EventBus:
    """轻量级事件总线。
    
    发布者 emit 事件，订阅者异步接收。
    Qt 主线程的 QTimer.singleShot(0, ...) 保证回调在主线程执行。
    """
    
    def __init__(self) -> None:
        self._handlers: dict[str, list[Callable]] = defaultdict(list)
    
    def subscribe(self, event_type: str, handler: Callable) -> None:
        self._handlers[event_type].append(handler)
    
    def emit(self, event_type: str, payload: Any = None) -> None:
        for handler in self._handlers[event_type]:
            # 经 QTimer.singleShot(0, ...) 投递到主线程
            QTimer.singleShot(0, lambda h=handler, p=payload: h(p))


# 事件类型常量
class Events:
    SCREENSHOT_CAPTURED = "screenshot.captured"
    CAPTURE_COMPLETED = "capture.completed"
    API_REPLY_RECEIVED = "api.reply.received"
    REPLY_DEQUEUED = "reply.dequeued"
    DANMU_DISPLAYED = "danmu.displayed"
```

### 演进路径

1. **Phase 1：引入 EventBus 基础设施**（低风险）
   - 新建 `app/events.py`，实现轻量级 EventBus
   - 单测覆盖事件订阅与发布

2. **Phase 2：抽离回复分发为独立消费者**（中风险，依赖 Top 1 完成）
   - `_consume_reply_queue` 改为 `emit(Events.REPLY_DEQUEUED, batch)`
   - 桌宠 / 浮动面板 / 横向 overlay 各自订阅 `REPLY_DEQUEUED` 事件
   - 新增分发通道只需 subscribe，不需修改 `_consume_reply_queue`

3. **Phase 3：主链路其他环节事件化**（高风险，长期）
   - 截图完成、API 回复、弹幕上屏等环节改为事件驱动
   - 保留主链路不变量检查（scene_generation、MAX_IN_FLIGHT）

### 风险提示

- **事件顺序性**：Qt 主线程事件循环保证 FIFO，但需确认 scene_generation 不变量不被破坏
- **调试困难**：事件驱动链路调试比同步调用复杂，需引入 trace_id 关联
- **过度解耦风险**：简单链路不应强行事件化，应聚焦于多消费者场景（如回复分发）

### 预期收益

- **可扩展性**：新增弹幕分发通道只需 subscribe，不触达主链路
- **可维护性**：`_consume_reply_queue` 从 277 行缩减到 ~30 行
- **可测试性**：各消费者独立单测，不需构造完整 DanmuApp

## 4.3 前端工程化升级

### 现状分析

当前前端栈：
- 32 个 JS 模块在 `web/static/modules/`，无构建工具链
- 6 个 CSS 文件（`warm-tokens.css` 等）手工管理
- `web/static/build_index_html.py` 是前端更新的强制步骤（用户规则），将 `partials/*.html` 拼接到 `index.template.html` 生成 `index.html`
- 无 npm / package.json / 依赖管理
- 无 TypeScript，无类型检查
- 无 minification / tree-shaking / source map
- 无 HMR（热模块替换），改前端需重启应用

### 目标状态

引入 Vite 构建工具链，统一管理前端资源：

```
web/
├── package.json
├── vite.config.ts
├── tsconfig.json
├── src/
│   ├── main.ts             # 入口
│   ├── modules/            # 现有 32 个 JS 模块迁移为 TS
│   ├── styles/             # 现有 6 个 CSS 迁移
│   └── partials/           # 现有 5 个 HTML 片段
└── dist/                   # 构建产物（替代当前 index.html + app.js）
    ├── index.html
    ├── assets/
    │   ├── app.[hash].js
    │   └── warm-tokens.[hash].css
    └── ...
```

### 演进路径

1. **Phase 1：引入 Vite 但保持现有 JS**（低风险）
   - 新建 `web/package.json`、`web/vite.config.js`
   - 配置 Vite 处理现有 JS 模块与 CSS
   - 构建产物输出到 `web/static/dist/`
   - `app/web_console.py` 改为 serve `dist/` 目录
   - 保留 `build_index_html.py` 作为过渡（生成 partials 注入到 Vite 入口）

2. **Phase 2：迁移到 TypeScript**（中风险）
   - JS 文件逐步改名为 `.ts`，添加类型注解
   - 配置 `tsconfig.json` 启用 strict 模式
   - 与后端 Pydantic 模型共享类型定义（可用 `pydantic-to-typescript` 或手工同步）

3. **Phase 3：废弃 build_index_html.py**（低风险）
   - Vite 原生支持 HTML 片段注入
   - 删除 `build_index_html.py` 与 `index.template.html`
   - 前端更新不再需要运行 Python 脚本

### 风险提示

- **打包体积**：需引入 minification 与 tree-shaking 减小体积
- **WebView2 兼容性**：需确认 Vite 构建产物的 ES 版本与 WebView2 兼容
- **开发流程变更**：前端开发者需安装 Node.js，CI 需增加 `npm ci` 步骤
- **过渡期复杂度**：Phase 1 期间存在双构建系统（Vite + build_index_html.py）

### 预期收益

- **开发体验**：HMR 热更新，改前端不需重启应用
- **可维护性**：TypeScript 类型检查减少运行时错误
- **性能**：minification + tree-shaking 减小资源体积
- **生态**：可使用 npm 生态（如 Vue/React 组件、Tailwind JIT 等）

## 4.5 不建议的演进方向

为避免过度设计，以下方向**不推荐**在当前阶段推进：

1. **微服务化**：DanmuAI 是单体桌面应用，微服务化无收益反而增加复杂度
2. **跨平台（macOS/Linux）**：Overlay 与 Win32 API 强耦合，跨平台成本远高于收益
3. **GraphQL 替代 REST**：当前 ~40 条 REST 路由已足够，GraphQL 引入复杂度无对应收益
4. **引入 ORM**：当前 SQLite 操作已封装良好（ConfigStore + WAL），ORM 增加抽象层无收益
5. **全面 async/await**：Qt 主线程 + QThreadPool 模型成熟，全面异步化会破坏 Qt 集成

**原则**：演进应聚焦于「降低耦合、提升可测试性、改善开发体验」，而非追逐技术潮流。每一步演进都应有明确的可衡量收益与回滚路径。

## 4.6 与短期优化的衔接

| 短期优化（Top 1-5） | 为长期演进铺路 |
|---------------------|----------------|
| Top 1 抽离主链路 | → 事件驱动化的前置条件（Phase 2 依赖主链路已抽离） |
| Top 2 修复收口私有字段 | → 依赖注入 Container 的前置条件（Container 需显式接口） |
| Top 3 修复层级倒置 | → 依赖注入 Container 的前置条件（层级清晰才能注入） |
| Top 4 异常层次 | → 可观测性提升的基础（统一异常便于日志聚合） |
| Top 5 拆分超大文件 | → 模块化独立演进的基础（小文件更易迁移到 Container） |

**核心原则**：短期优化应避免引入长期演进的复杂度，但应为长期演进预留接口。例如 Top 1 抽离主链路时，方法签名应设计为可被事件总线调用，但不必立即引入 EventBus。
