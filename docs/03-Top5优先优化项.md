## Top 1：抽离 DanmuApp 主链路为独立 GenerationPipeline 服务

> **状态：已完成（W-GENPIPELINE-EXTRACT，2026-06 后）**。回复消费逻辑已迁至 `app/application/generation_pipeline.py`；DanmuApp 保留 `_consume_reply_queue` façade；`reply_timer` 所有权在 `app/main_lifecycle_mixin.py:155-158`。下文为历史问题描述，供背景参考。

### 问题描述（历史）

`DanmuApp` 类经 8 个 mixin 组合后整体约 4170 行，其中主链路回复消费方法 `_consume_reply_queue`（`main.py:754-1031`）单方法长达 **277 行**，包含桌宠气泡 / 浮动面板 / 横向 overlay 三条分发分支。AI 回复处理 `_on_ai_reply`（`main.py:547`）混杂回复解析、统计更新、诊断记录、回复分发等多重职责。

### 当前影响

- **可维护性下降**：单方法 277 行难以阅读与定位 bug
- **测试困难**：`_consume_reply_queue` 依赖 DanmuApp 实例的 50+ 字段，无法独立单测
- **修改风险高**：任何分发分支调整都需触碰主链路核心方法
- **mixin 耦合加剧**：所有 mixin 通过 `self.*` 访问 `self.reply_buffer`、`self._scene_generation`、`self.engine` 等共享状态

### 优化方案

抽离 `app/application/generation_pipeline.py` 作为独立服务，DanmuApp 持有引用并委托调用。

**结构示例**：

```python
# app/application/generation_pipeline.py
from __future__ import annotations
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from main import DanmuApp


class GenerationPipeline:
    """主链路回复消费与分发服务。
    
    从 DanmuApp._consume_reply_queue / _on_ai_reply 抽离，
    DanmuApp 持有引用并委托调用。
    """
    
    def __init__(self, app: "DanmuApp") -> None:
        self._app = app
        # 注入依赖而非访问 self._app.*
        self._engine = app.engine
        self._reply_buffer = app.reply_buffer
        self._pet_facade = app.pet_facade
        self._floating_panel = app.floating_panel_engine
        self._overlay = app.overlay
    
    def consume_reply_queue(self) -> None:
        """从 reply_buffer 取出回复，分发到三条通道。"""
        batch = self._reply_buffer.dequeue_batch()
        if not batch:
            return
        
        # 三条分发分支独立方法
        if self._app._pet_barrage_mode_enabled():
            self._dispatch_to_pet(batch)
        elif self._app._floating_panel_v2_enabled():
            self._dispatch_to_floating_panel(batch)
        else:
            self._dispatch_to_overlay(batch)
    
    def _dispatch_to_pet(self, batch: list) -> None:
        """桌宠气泡分发。"""
        ...
    
    def _dispatch_to_floating_panel(self, batch: list) -> None:
        """浮动面板分发。"""
        ...
    
    def _dispatch_to_overlay(self, batch: list) -> None:
        """横向 overlay 分发。"""
        ...
```

**DanmuApp 委托**：

```python
# main.py
class DanmuApp(...):
    def __init__(self, ...):
        ...
        self._generation_pipeline = GenerationPipeline(self)
    
    def _consume_reply_queue(self) -> None:
        """委托给 GenerationPipeline（保留方法签名向后兼容）。"""
        self._generation_pipeline.consume_reply_queue()
```

### 实施难度：中-高

**风险点**：
- `_consume_reply_queue` 依赖 `scene_generation` 不变量（`_visual_reply_stale_reason` 检查）
- 三条分发分支访问的字段需完整迁移
- 必须保证 Qt 主线程执行（GenerationPipeline 方法仍需在主线程调用）

### 建议步骤

1. **Phase 1**：抽取 `_dispatch_to_overlay`（最简单分支）到 `GenerationPipeline._dispatch_to_overlay`，DanmuApp 委托调用
2. **Phase 2**：抽取 `_dispatch_to_floating_panel` 与 `_dispatch_to_pet`
3. **Phase 3**：将 `_on_ai_reply` 中的回复解析与统计更新抽离
4. **每 Phase 验证**：跑 `tests/test_p0_main_flow.py` + `tests/test_reply_enqueue.py` + `tests/test_reply_pipeline_log.py`，分批 `-q -x`
5. **最终**：跑 `python scripts/boundary_guard.py` 确认未触达禁止区

## Top 2：修复 application/ 边界收口层的私有字段直读

### 问题描述

`app/application/__init__.py` docstring 声明「只读投影、状态快照与 Web 配置写入。不含 QTimer/QThreadPool，不触发主链路」。但实际有 **5 个文件**通过 `getattr` / `__dict__` 直接读取 DanmuApp 私有字段，违反收口声明。

### 当前影响

- **收口失效**：application/ 层直接耦合 DanmuApp 内部实现，DanmuApp 字段重命名会跨层影响
- **新增 application/ 文件可能延续反模式**：无强制约束阻止后续开发者继续直读私有字段
- **测试困难**：application/ 单测需构造完整 DanmuApp 实例才能满足 getattr fallback

### 证据清单

| 文件 | 行号 | 直读的私有字段 |
|------|------|----------------|
| `generation_pipeline_state.py` | 26-34 | `_latest_displayed_round`、`_latest_requested_screenshot_id`、`_latest_queued_screenshot_id`、`_latest_displayed_screenshot_id`（经 getattr） |
| `runtime_state.py` | 91-157 | `_total_input_tokens`、`_total_output_tokens`、`_start_time`、`_web_error_message`、`_web_error_is_error`、`_cached_danmu_lines`、`_cached_layout_mode`（经 getattr fallback） |

## Top 4：引入统一异常层次与 web_api 装饰器

### 问题描述

**问题 A：异常无层次结构**
- 全项目仅 2 个自定义异常类：
  - `ConfigStoreCryptoUnavailableError(RuntimeError)`（`app/config_store.py:130`）
  - `DanmuTtsError(Exception)`（`app/tts_providers.py:62`）
- 分别继承不同基类，无共享父类，无法统一捕获

**问题 B：web_api 鉴权重复**
- `app/web_api/` 下 68 处 `check_token(authorization)` 内联调用，跨 8 文件
- `routes.py` 占 50 次，每个写路由处理函数第一行都是 `check_token(authorization)`
- 无装饰器封装，新增路由易遗漏

**问题 C：异常捕获过宽**
- 53 处 `except Exception:` 跨 27 文件
- 部分场景应捕获更具体异常类型

### 当前影响

- **错误处理不一致**：调用方无法统一捕获项目异常
- **鉴权易遗漏**：新增路由忘记 `check_token` 会导致未授权访问
- **调试困难**：`except Exception` 吞掉异常细节
- **HTTP 状态码映射分散**：`routes.py:164-188 _invoke_main` 集中映射，但其他路由文件可能未走此路径

### 优化方案

**方案 A：定义统一异常基类**

**方案 B：引入 `@require_auth` 装饰器**

```python
# app/web_api/auth.py（新建）
from functools import wraps
from typing import Callable, Optional

from fastapi import HTTPException, Request, status


def require_auth(check_token: Callable[[Optional[str]], bool]) -> Callable:
    """FastAPI 路由鉴权装饰器。
    
    用法：
        @router.post("/api/foo")
        @require_auth(check_token)
        def create_foo(request: Request, ...):
            ...
    """
    def decorator(func: Callable) -> Callable:
        @wraps(func)
        def wrapper(*args, request: Request, **kwargs):
            authorization = request.headers.get("Authorization")
            if not check_token(authorization):
                raise HTTPException(
                    status_code=status.HTTP_401_UNAUTHORIZED,
                    detail="Invalid or missing Bearer token",
                )
            return func(*args, request=request, **kwargs)
        return wrapper
    return decorator
```

**路由改造示例**：

```python
# 修改前
@router.post("/api/persona")
def create_persona(request: Request, payload: PersonaCreatePayload):
    check_token(request.headers.get("Authorization"))
    ...

# 修改后
@router.post("/api/persona")
@require_auth(check_token)
def create_persona(request: Request, payload: PersonaCreatePayload):
    ...
```

### 实施难度：中

**风险点**：
- 异常基类迁移需保证现有 `except RuntimeError` / `except Exception` 仍能捕获
- 装饰器需正确处理 FastAPI 的依赖注入（request 参数）
- 68 处鉴权调用需逐一改造，工作量大

### 建议步骤

1. **Phase 1**：创建 `app/errors.py`，定义异常层次
2. **Phase 2**：迁移 `ConfigStoreCryptoUnavailableError` 与 `DanmuTtsError` 继承 `AppError`
3. **Phase 3**：创建 `app/web_api/auth.py`，实现 `@require_auth` 装饰器
4. **Phase 4**：先在 `routes.py` 试点改造 5 个路由，验证装饰器可用
5. **Phase 5**：批量改造剩余 63 处
6. **每 Phase 验证**：跑 `tests/test_web_auth.py` + `tests/test_web_routes.py`，分批 `-q -x`

## Top 5：拆分超大文件（config_store 子包 / danmu_engine 子包）

> **状态：已完成（2026-06 后）**。`app/config_store/`（`storage.py` 1196 行 + `pool.py` 等）与 `app/danmu_engine/`（`track.py` / `render.py` / `screen.py` 等）已拆分子包。下文为历史问题描述，供背景参考。

- 密钥备份（`_backup_corrupted_key_file`）

**danmu_engine.py 职责混杂**：
- 多轨道 Track 数据结构（`DanmuTrack`、`DanmuItem`）
- 轨道选择（`_pick_track` 三段加权随机）

## 优化项优先级矩阵

| Top | 影响范围 | 实施难度 | 见效速度 | 推荐顺序 |
|-----|----------|----------|----------|----------|
| 1 抽离主链路 | 高（主链路核心） | 中-高 | 中（需分 Phase） | 2 |
