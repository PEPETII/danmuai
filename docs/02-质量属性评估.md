# 02 - 质量属性评估

> **历史架构快照（2026-07-02）**：评分与数量只对采集时点有效，正文中的 8 Mixin、旧单文件路径和行数不代表当前源码。现行事实入口见 [docs/README.md](README.md) 顶部的权威文档清单。
>
> 本章节从 6 个维度对 DanmuAI 进行质量评分（1-5 分，5 为优秀），每维度附评分理由、关键风险点（带文件:行号引用）与改进方向。所有评分基于 [06-探索事实附录.md](06-探索事实附录.md) 的事实证据。

## 2.1 评分总览

| 维度 | 评分 | 关键依据 |
|------|------|----------|
| 可维护性 | 3/5 | DanmuApp ≈3952 行 God Object；10 个文件超 500 行；mixin 通过 self.* 共享状态非真解耦 |
| 可测试性 | 3/5 | 700+ 用例覆盖充分，但全量执行耗内存需分批；DanmuApp 强耦合 Qt 难单测 |
| 性能与资源利用 | 4/5 | WAL+缓存读路径优化；QThreadPool 限流；但 MAX_IN_FLIGHT=1 串行化限制吞吐 |
| 安全性 | 4/5 | Fernet 加密；icacls 权限；Bearer Token；但密钥丢失不可恢复 |
| 可扩展性 | 2/5 | 8-mixin 共享 self.* 非真解耦；新增 provider 需触达多文件；层级倒置 |
| 部署与运维友好度 | 4/5 | Velopack 自动更新；CI 完整；但 Windows-only 无跨平台 |

**综合评分：3.3/5** — 功能完备但耦合度高，处于「需要重构窗口期」。

## 2.2 可维护性（3/5）

### 评分理由

项目文档化程度高（AGENTS.md 详尽），命名一致性强（mic_*/tts_*/persona_*/main_*_mixin 等模式清晰），但核心类过大且 mixin 非真正解耦。

### 关键风险点

1. **God Object：DanmuApp 类整体约 3952 行**
   - 证据：`main.py:97-107` 定义类继承 8 mixin + QObject；main.py 763 行 + 8 mixin 3189 行 ≈ 3952 行（2026-07-05 复核）
   - 100+ 方法，`__init__` 初始化 50+ 字段
   - `_consume_reply_queue` 已委托 `GenerationPipeline.consume_reply_queue`（W-GENPIPELINE-EXTRACT 已完成）

2. **10 个文件超过 500 行**
   - `app/config_store/storage.py`（1196 行）：加密 + 锁 + SQLite + 迁移 + 弹幕池 CRUD 多职责（已拆分子包）
   - `app/danmu_engine/`（子包 ≈1401 行）：轨道 + 渲染 + 调度（**已拆分**，2026-06 后）
   - `app/main_lifecycle_mixin.py`（798 行）：初始化 + 生命周期 + 错误处理 + 统计 flush
   - `app/ai_client_requests.py`（734 行）：双 provider HTTP 细节
   - `app/overlay.py`（703 行）：Qt 渲染 + Win32 互操作 + 性能优化
   - `app/main_display_mixin.py`（616 行）：显示编排 + bililive 推送
   - `app/danmu_pool.py`（597 行）：弹幕库 CRUD + 同屏补足 + diff 更新
   - `app/model_catalog.py`（543 行）、`app/floating_panel_engine.py`（542 行）、`app/model_providers.py`（538 行）

3. **mixin 通过 `self.*` 共享状态，非真正解耦**
   - 所有 8 个 mixin 访问同一 DanmuApp 实例的 `self.config`、`self.engine`、`self.reply_buffer`、`self._scene_generation` 等字段
   - mixin 之间无显式接口契约，重命名一个字段会跨 mixin 影响多处

4. **方法重复定义**
   - `build_status_snapshot`：`main.py:123` 与 `main_web_facade_mixin.py:65` 重复（类体内覆盖 mixin）
   - `apply_web_config_payload`：`main.py:126` 与 `main_web_facade_mixin.py:133` 重复

### 改进方向

- 详见 [03-Top5优先优化项.md](03-Top5优先优化项.md) Top 1（抽离主链路）与 Top 5（拆分超大文件）
- 长期方向见 [04-长期演进建议.md](04-长期演进建议.md) 依赖注入容器化

## 2.3 可测试性（3/5）

### 评分理由

测试覆盖非常充分（192 文件 / 700+ 用例 / 39066 行），共享假对象设计良好（`tests/fakes.py` 440 行），但 DanmuApp 强耦合 Qt 导致单测困难，全量执行需分批避免内存耗尽。

### 关键风险点

1. **全量测试耗尽内存**
   - 证据：AGENTS.md §7 明确禁止 `python -m pytest tests/`，强制分批 `-q -x`
   - 700+ 用例占用 Windows 开发机内存导致卡顿
   - 反映主链路对 Qt 主线程强耦合，测试需初始化大量 QObject

2. **DanmuApp 难以独立单测**
   - 必须用 `DanmuApp.__new__(DanmuApp)` + `bind_minimal_danmu_app(app, **overrides)`（`tests/conftest.py`）绕过 `__init__`
   - 单个 mixin 方法测试需初始化整个 DanmuApp 状态

3. **Pydantic Payload 嵌套定义导致测试导入困难**
   - `app/web_api/routes.py:60-159` 将 ~15 个 Payload 类定义为 `register_web_routes` 函数内部嵌套类
   - 测试无法直接 `from app.web_api.routes import PersonaCreatePayload`

4. **`_pick_track` 加权随机需 monkeypatch**
   - `app/danmu_engine/track.py:_pick_track` 三段加权随机（idle → random.choice；acceptable → random.choices(weights=1/(1+count))；满载 → tail_edge + random.uniform(50, 250)）
   - 测试需 `monkeypatch` `random.choices` 才能断言确定性轨道

5. **Overlay 单测需真实 QApplication**
   - `app/overlay.py` 测试需 `QApplication` + `overlay.show()` + `processEvents()`
   - `_target_interval_ms()` 在不可见时返回 0，无法纯逻辑测试

### 改进方向

- 将 Pydantic Payload 提取到模块级（`app/web_api/payloads.py`）
- 抽离主链路为独立服务（见 Top 1），降低 Qt 耦合
- 引入 pytest-xdist 或 pytest-split 支持并行测试

## 2.4 性能与资源利用（4/5）

### 评分理由

关键路径已优化（WAL 模式 + 内存缓存 + QThreadPool 限流），图像压缩无临时文件，但 MAX_IN_FLIGHT=1 串行化限制吞吐。

### 关键优势

1. **SQLite 读路径优化**
   - `PRAGMA journal_mode=WAL`（`app/config_store/storage.py`）：读不阻塞写
   - `PRAGMA busy_timeout=5000`（`storage.py`）：写冲突等待 5s
   - `check_same_thread=False` + `cached_statements=256`（`config_store.py:146`，显式放大默认 128）
   - 读路径走内存 `_cache` 不持 `_write_lock`

2. **QThreadPool 限流**
   - `MAX_IN_FLIGHT=1`（`main_helpers.py:24`）避免冷启动连打
   - 视觉请求与麦克风请求独立限流（`MAX_MIC_IN_FLIGHT=1`）

3. **图像压缩无临时文件**
   - `app/image_compress.py`：PIL + JPEG + Base64 直接 in-memory，`max_width=1024`、`quality=85`

4. **diff-based 增量更新**
   - `set_custom_danmu_pool_for_store` 已改为 diff-based（`_diff_custom_danmu_pool` 计算 to_add/to_remove）
   - 大批量替换受 `CUSTOM_DANMU_POOL_MAX=20000` 上限约束

5. **回复队列自适应延迟**
   - `AIReplyFIFOBuffer`（`reply_queue.py`，`max_items=8`）+ 自适应延迟 100–1000ms
   - 由 `_estimated_reply_gap_ms` 计算（100/120/200/500/1000ms 分档）

### 关键风险点

1. **MAX_IN_FLIGHT=1 串行化限制吞吐**
   - 视觉 AI 请求完全串行，无法并行处理多截图
   - 设计上是避免冷启动连打，但也限制了高并发场景

2. **`get_custom_danmu_pool_for_store` 不分页读全表**
   - 默认上限 20000，在主线程调用时窗口化渲染可能 hang
   - 证据：AGENTS.md §A.5.1 标注

3. **`_consume_reply_queue` 单方法 277 行**
   - 主线程同步执行三条分发分支（桌宠/浮动面板/横向 overlay）
   - 任一分支阻塞会拖慢整个回复消费

4. **WebView2 冷启动慢**
   - `webview_shell.py` 设 `_LOAD_TIMEOUT_SEC=25` / `_FROZEN_LOAD_TIMEOUT_SEC=25`
   - WebView2 冷启动可能 >12s

### 改进方向

- 评估 MAX_IN_FLIGHT 提升至 2-3 的可行性（需保证 scene_generation 不变量）
- `_consume_reply_queue` 三条分支拆分为独立 worker
- 弹幕库读取分页化

## 2.5 安全性（4/5）

### 评分理由

加密、权限、鉴权机制完善，但密钥丢失不可恢复且无密钥轮换机制。

### 关键优势

1. **Fernet 对称加密**
   - `cryptography.fernet.Fernet` 对敏感配置（API Key）加密存储
   - 密钥文件：`%APPDATA%/DanmuAI/.key`
   - 无 cryptography 时 fail-closed：抛 `ConfigStoreCryptoUnavailableError`（`config_store.py:130`）

2. **文件权限控制**
   - `_restrict_key_file_permissions`（`config_store.py:67`）
   - Windows 上 `icacls /inheritance:r /grant:r USERNAME:F`

3. **Web Console Bearer Token**
   - 写接口需要 `Authorization: Bearer <token>`
   - 启动时 `secrets.token_urlsafe(24)` 生成

4. **密钥损坏 best-effort 备份**
   - 备份到 `.key.bak.<timestamp>`

5. **GET 自定义模型返回掩码 apiKey**
   - 防止敏感信息泄露

6. **日志脱敏**
   - `SanitizedLogger` 用于脱敏 API Key

### 关键风险点

1. **密钥丢失不可恢复**
   - 丢失 `%APPDATA%/DanmuAI/.key` → 已加密 Key 不可恢复
   - 无密钥轮换 / 密钥托管机制

2. **`.backend-doctor.toml` 禁用安全规则**
   - 证据：`disabled-rules = ["security/hardcoded-secret", "node/dead-export"]`
   - 禁用了硬编码 secret 检测（可能误报多，但降低了安全审计能力）

3. **Supabase 配置暴露风险**
   - `DANMU_SUPABASE_URL` / `DANMU_SUPABASE_ANON_KEY` 通过环境变量
   - `web/static/supabase-config.example.js` 提供示例（需确认 .gitignore 覆盖实际配置）

4. **单实例锁激活失败需主动 sys.exit**
   - `SingleInstanceGuard` 激活失败需在 main 中主动 `sys.exit`，否则会并发启动
   - 依赖开发者记忆，无强制机制

### 改进方向

- 引入密钥轮换机制（如密钥版本号 + 多密钥支持）
- 重新启用 `security/hardcoded-secret` 规则并修复误报
- Supabase 配置经后端代理而非前端直连

## 2.6 可扩展性（2/5）

### 评分理由

新增子系统需触达多个文件，mixin 模式难以横向扩展，存在层级倒置。

### 关键风险点

1. **8-mixin 共享 self.* 非真解耦**
   - 新增 mixin 需访问 DanmuApp 实例所有字段，无显式接口契约
   - 字段重命名跨 mixin 影响

2. **新增 AI provider 需触达多文件**
   - 当前 5 平台 / 9 预设，新增需修改：
     - `app/providers/adapters/` 新增适配器
     - `app/providers/registry.py` 注册 host entry
     - `app/model_providers.py` 添加预设
     - `app/model_catalog.py` 添加定价元数据
     - 可能需修改 `app/ai_client.py` 或 `ai_client_requests.py`

3. **层级倒置**
   - `app/application/bililive_dm_push_service.py:13-17` 反向 import `app.web_api.bililive_dm_push`
   - 违反分层原则，阻碍 application 层独立演进

4. **边界收口层部分失效**
   - 5 个 application/ 文件直读 DanmuApp 私有字段（详见 [03-Top5优先优化项.md](03-Top5优先优化项.md) Top 2）
   - 新增 application/ 文件可能延续此反模式

5. **路由注册集中在单函数**
   - `app/web_api/routes.py:54 register_web_routes()` 集中注册 ~40 条路由
   - 新增路由需修改此函数，且 Payload 类嵌套定义在函数内

6. **配置键分散管理**
   - `WEB_CONFIG_KEYS` 白名单在 `app/application/config_service.py`
   - 弹幕池配置经独立路由 `/api/danmu-pool/settings`，**不进** `PUT /api/config`
   - 截图区域经独立路由 `POST/GET /api/capture-region/*`，**不进** `PUT /api/config`
   - 配置键入口分散，新增配置需判断归属

### 改进方向

- 详见 [03-Top5优先优化项.md](03-Top5优先优化项.md) Top 2、Top 3
- 长期方向见 [04-长期演进建议.md](04-长期演进建议.md) 依赖注入容器化与事件驱动化

## 2.7 部署与运维友好度（4/5）

### 评分理由

CI 完整，Velopack 自动更新成熟，Windows 打包链路完善，但仅支持 Windows 无跨平台。

### 关键优势

1. **CI 完整**
   - `.github/workflows/ci.yml` 两个 Job：
     - `test`：ruff check + 全量 pytest（windows-latest, Python 3.12）
     - `pack-windows`：PyInstaller + Velopack 打包验证
   - 产物验证：`release/velopack/PEPETII.DanmuAI-win-Setup.exe` + `.nupkg` + `releases.win.json`

2. **Velopack 自动更新**
   - `velopack>=1.2.0,<2`
   - `app/velopack_runtime.py` 处理 import_error
   - `scripts/publish_windows_release.ps1`、`upload_r2_release.ps1`、`upload_github_release.ps1` 完整发布脚本

3. **Lint 配置规范**
   - ruff target py312，line-length 100
   - select E/F/I/W，per-file-ignores 针对测试放宽

4. **单实例锁**
   - `SingleInstanceGuard` 防止并发启动

5. **诊断能力**
   - `/api/diagnostics` SSE 流式诊断
   - `reason=` 字符串结构化日志（null_pixmap、scene_generation_lagged 等）
   - 环境变量 `DANMU_API_SCHEDULE_DEBUG=1`、`DANMU_REPLY_PIPELINE_LOG=1` 等可开启详细日志

6. **启动参数拒绝统一**
   - `app/main_launch.py:check_deprecated_launch_args()` 集中处理

### 关键风险点

1. **Windows-only 无跨平台**
   - 依赖 Win32 API（`app/win32_overlay_zorder.py`、`icacls` 权限）
   - `%APPDATA%` 路径硬编码
   - 无 macOS / Linux 支持

2. **无 Docker 化**
   - 桌面应用天然不适合 Docker，但开发环境无标准化容器
   - 新开发者需手动配置 Windows + Python 3.12 环境

3. **boundary_guard baseline 缺失**
   - `docs/final-architecture-baseline.md` 当前缺失（AGENTS.md §A.9 标注）
   - boundary_guard baseline 规则会失败

4. **无 mypy 类型检查**
   - 仅 ruff，无静态类型检查
   - 类型注解覆盖率 78%（抽样），但无强制检查

5. **无 pre-commit hooks**
   - 依赖 CI 检查，本地提交前无自动化校验

### 改进方向

- 引入 mypy（至少对 app/ 启用 strict 模式）
- 配置 pre-commit hooks（ruff + mypy）
- 补建 `docs/final-architecture-baseline.md` 恢复 boundary_guard baseline
- 长期评估跨平台可行性（Overlay 与 Win32 强耦合，成本高）
