## 1. 项目总体判断

### 1.1 项目性质

DanmuAI 是一个 Windows 桌面 AI 弹幕工具：截取所选显示器全屏 → 调用视觉模型生成弹幕 → 以 Qt 透明置顶浮层滚动展示，为直播主播提供轻量、隐私友好的 AI 弹幕助手。

**技术栈**：PyQt6 + FastAPI/uvicorn + SQLite(WAL + Fernet 加密) + pywebview + httpx + PyInstaller/Velopack 双轨打包。

### 1.2 架构成熟度

| 维度 | 评价 | 证据 |
|------|------|------|
| 架构清晰度 | **良好** — 单例 `DanmuApp`（8 Mixin）+ 3 隔离 QThreadPool + Web façade 模式 | [main.py:94-104](../main.py#L94-L104) |
| 测试覆盖 | **良好** — 200+ 测试文件，覆盖主链路/弹幕/Web/麦/桌宠/TTS/烂梗/配置/浮动面板 | `tests/` 目录 |
| 治理流程 | **完善** — `.local-ai/workorders/` 工单系统 + `boundary_guard` 架构边界检查 + 维护者登记表 | `.local-ai/workorders/`、`scripts/boundary_guard/` |
| 依赖管理 | **合理** — 16 个运行时依赖全部 pin 在 major 内，有 `requirements-dev.txt` | `requirements.txt` |
| 文档治理 | **漂移严重** — AGENTS.md 引用的 8+ docs 文档不存在、workorders 路径错位、`final-architecture-baseline.md` 缺失 | 见 §4.5 |

### 1.3 运行链路稳定性

主链路 `screenshot_timer → _on_normal_capture_tick → _schedule_capture → CaptureRunnable → _on_capture_completed → _trigger_api_call → AiRunnable → _on_ai_reply → _consume_reply_queue` 设计合理，有 `scene_generation` 场景指纹版本淘汰过期回复、`MAX_IN_FLIGHT=1` 串行化视觉请求、连续 5 次失败退避等保护机制。线程模型明确：截图/回复出队/Qt 对象在主线程，AI HTTP 在 QThreadPool，HTTP 线程写 Qt 必须经 `WebConsoleBridge` 信号。

### 1.4 最大风险所在

1. **文档与代码漂移**（§4.5）：AGENTS.md 作为权威协作文档存在 4 处过时技术描述 + 8+ 断裂 docs 链接，会误导后续工单基于错误前提改动
2. **路径穿越隐患**（§2.1）：`pet_asset_path` 用户可控且无校验
3. **进程脆弱性**（§2.2）：`global_exception_hook` 任一未捕获异常即杀进程
4. **加密降级**（§2.3）：cryptography 不可用时 API Key 退化为 base64
5. **并发陷阱**（§2.4）：`_write_lock` 非 RLock 的间接持锁路径脆弱

**总体结论**：项目架构成熟、测试覆盖良好、治理流程完善，**适合继续开发**，无阻塞性技术问题（除 `boundary_guard` 依赖文件缺失外）。需优先处理少数安全与并发陷阱，并校正文档漂移。

## 2. 高风险问题

### 2.1 H1 — `pet_asset_path` 路径未校验（路径穿越）

**问题描述**：Web 控制台可通过 `POST /api/pet/settings` 直接设置 `pet_asset_path`，该路径在 `_resolve_pack_dir` 中被直接用作桌宠资源目录，**无任何路径校验或沙箱约束**。攻击者（或本机恶意进程拿到 Bearer token）可指向任意目录加载 `pet.json` + spritesheet，间接读取任意路径文件内容。

**影响范围**：桌宠资源加载链路；本机任意目录文件可被读取（经 pet 渲染）

**证据位置**：

[app/pet/pet_assets.py:152-158](../app/pet/pet_assets.py#L152-L158)：

```python
def _resolve_pack_dir(config: "ConfigStore") -> Path:
    source = str(config.get("pet_asset_source", "builtin") or "builtin").strip().lower()
    if source == "local":
        custom = str(config.get("pet_asset_path", "") or "").strip()
        if custom:
            return Path(custom)   # ← 直接使用，无校验
    return BUILTIN_PET_DIR
```

`POST /api/pet/settings` 路由允许设置 `asset_path`（经 `PetSettingsPayload.asset_path`），无路径白名单/归一化校验。

**对比**：[app/font_registry.py:22-24](../app/font_registry.py#L22-L24) 用 `safe_filename(sha256, suffix)` 生成文件名，不使用用户提供的文件名，**安全**。

**可能触发场景**：
1. 攻击者拿到本机 Web Console Bearer token（启动时 `secrets.token_urlsafe(24)` 生成，见 [app/web_console.py:402](../app/web_console.py#L402)）
2. 调用 `POST /api/pet/settings` 设置 `pet_asset_source=local` + `pet_asset_path=C:\Users\victim\secret`
3. 桌宠加载该目录的 `pet.json` + spritesheet，间接泄露文件存在性/内容

**建议修复方式**：校验 `pet_asset_path` 必须在白名单目录（如 `%APPDATA%/DanmuAI/pet-packs/`）内，或拒绝绝对路径，使用 `Path.resolve()` 后检查是否在允许根目录下。

**是否建议立即修复**：**是（P0）** — 虽需本机 token 才能利用，但属明确安全缺口

### 2.2 H2 — `global_exception_hook` 任一未捕获异常即 `sys.exit(1)` 杀进程

**问题描述**：全局异常钩子对**任何**未捕获异常（除 `KeyboardInterrupt`/`SystemExit` 与 Qt "has been deleted" RuntimeError）都执行 `sys.exit(1)` 终止进程，且先弹模态 `QMessageBox` 阻塞。生产环境中单次偶发异常即杀进程，稳定性不友好。

**影响范围**：整个应用进程稳定性；任一线程未捕获异常传导到主线程即触发

**证据位置**：

[app/main_launch.py:59-82](../app/main_launch.py#L59-L82)：

```python
def global_exception_hook(exc_type, exc_value, exc_tb) -> None:
    if exc_type in (KeyboardInterrupt, SystemExit):
        return
    message = "".join(traceback.format_exception(exc_type, exc_value, exc_tb))
    try:
        logger = SanitizedLogger()
        logger.error(tr("app.unhandled_exception_log").format(message=message))
    except Exception:
        ...
    if issubclass(exc_type, RuntimeError) and "has been deleted" in str(exc_value):
        return   # ← 仅跳过 Qt 析构异常
    try:
        if QApplication.instance() is not None:
            msg_box = QMessageBox(QMessageBox.Icon.Critical)
            ...
            msg_box.exec()   # ← 模态阻塞
    except Exception:
        pass
    sys.exit(1)   # ← 任一异常即退出
```

**可能触发场景**：
1. AI 回复解析偶发异常（网络抖动、模型返回畸形 JSON）
2. Qt 内部偶发异常（非 "has been deleted" 类）
3. 任一 worker 线程未捕获异常经 `sys.excepthook` 传导（注意：Python `sys.excepthook` 仅对主线程异常触发，线程异常走 `threading.excepthook`，但 Qt 的某些路径会传导到主线程）

**建议修复方式**：
- 区分致命/非致命异常：仅 `SystemExit`/`MemoryError`/`KeyboardInterrupt` 触发退出
- 其他异常记录日志后继续运行（或仅重启受影响子系统）
- 移除模态 `QMessageBox` 阻塞，改用 Web 控制台状态栏提示

**是否建议立即修复**：**否（P1）** — 当前有 Qt 析构异常豁免，影响面有限；但建议尽快软化

### 2.3 H3 — cryptography 不可用时 API Key 退化为 base64（非加密）

**问题描述**：`cryptography` 包不可用时（如打包遗漏、依赖损坏），`_queue_secret_write` 退化为 base64 编码存储 API Key。base64 **仅是编码非加密**，任何能读取 `config.db` 的人可立即解码获得明文 key。虽有 `logger.warning(tr("config.insecure_store"))` 告警，但用户可能未注意到。

**影响范围**：所有加密配置字段（`api_key_encrypted`、`mic_api_key_encrypted`、`tts_api_key_encrypted`）

**证据位置**：

[app/config_store.py:362-369](file:///e:/test/danmu/app/config_store.py#L362-L369)：

```python
def _queue_secret_write(
    self, ...
) -> None:
    """Queue API key REPLACE/DELETE within an open transaction (caller holds _write_lock)."""
    if _HAS_CRYPTO and self._fernet:
        encrypted = self._fernet.encrypt(key.encode("utf-8")).decode("utf-8")
        pairs.append((encrypted_key, encrypted))
        ...
        return
    logger.warning(tr("config.insecure_store"))
    pairs.append((encoded_key, b64encode(key.encode("utf-8")).decode("utf-8")))   # ← base64 非加密
```

**风险加剧**：Fernet 密钥存 `%APPDATA%/DanmuAI/.key`，[app/config_store.py:62-67](file:///e:/test/danmu/app/config_store.py#L62-L67) 的 `_restrict_key_file_permissions` 用 `os.chmod(path, 0o600)` 但 **Windows 上 chmod 对密钥文件保护有限**（Windows ACL 未设置），且 `except Exception: pass` 静默忽略失败。

**可能触发场景**：
1. PyInstaller 打包遗漏 `cryptography` 依赖（虽有 `requirements.txt` 但打包配置可能漂移）
2. 用户环境 Python 损坏或 `cryptography` C 扩展加载失败
3. 密钥文件 `.key` 丢失时无法解密旧数据（AGENTS.md §A.5.1 已记录的"加密锁死"）

**建议修复方式**：
- 降级时**拒绝存储敏感字段**，强制要求 `cryptography` 可用
- 或在启动时检测 `_HAS_CRYPTO`，不可用时拒绝启动并提示用户
- 密钥文件权限在 Windows 上改用 `icacls` 设置 ACL

**是否建议立即修复**：**否（P2）** — 需平衡可用性与安全性；当前降级有告警

### 2.4 H4 — `_write_lock` 非 RLock，间接持锁路径脆弱

**问题描述**：`ConfigStore._write_lock` 是非可重入 `threading.Lock`（非 `RLock`），任何递归回调内再次获取会自死锁。`get_custom_models` 在检测到需升级时会调用 `set_custom_models`，后者内部调用 `set()` 再获取 `_write_lock`。当前调用链**不持锁调用 `get_custom_models`**，所以目前安全；但若未来有调用方在持 `_write_lock` 时调 `get_custom_models`，将立即死锁。

**影响范围**：配置存储层；死锁会导致整个应用挂起（主线程持锁阻塞）

**证据位置**：

[app/config_store.py:119](file:///e:/test/danmu/app/config_store.py#L119)：

```python
self._write_lock = threading.Lock()   # ← 非 RLock
```

[app/config_store.py:695-730](file:///e:/test/danmu/app/config_store.py#L695-L730)（`get_custom_models` → `set_custom_models` 间接持锁路径）：

```python
def get_custom_models(self) -> list:
    ...
    for model in parsed:
        ...
        if needs_encrypt:
            needs_upgrade = True
    if needs_upgrade:
        self.set_custom_models(result)   # ← 内部会获取 _write_lock
    ...
```

AGENTS.md §A.5.1 已明确警告此约束，`with_write_lock` 与 `set_flag` 的 docstring 也标注"不可重入"。

**可能触发场景**：未来工单在持 `_write_lock` 时调用 `get_custom_models`（或任何会触发 `set_custom_models` 的读路径）

**建议修复方式**：
- 将 `_write_lock` 改为 `threading.RLock`（允许同线程多次获取）
- 或在 `get_custom_models` 标注"禁止在持 `_write_lock` 时调用"并加运行时断言

**是否建议立即修复**：**否（P1）** — 当前不触发死锁；但属隐性陷阱，建议尽快改 RLock

### 2.5 H5 — SSE token 经 URL 传递、无时效机制

**问题描述**：Web Console Bearer Token 在启动时由 `secrets.token_urlsafe(24)` 生成，**进程生命周期内固定不变，无过期机制**。SSE 端点 `/api/diagnostics/events` 经 URL query 参数 `token` 传递（EventSource 不支持自定义 Header），token 可能经 Referer/日志/浏览器历史泄漏。

**影响范围**：Web Console 鉴权；虽仅绑 `127.0.0.1`（本机），但本机恶意进程可嗅探

**证据位置**：

[app/web_console.py:402](../app/web_console.py#L402)：

```python
self.token = secrets.token_urlsafe(24)   # ← 进程内固定，无过期
```

[app/web_api/routes.py:713-715](../app/web_api/routes.py#L713-L715)：

```python
async def diagnostics_events(token: str | None = None):
    # SSE 端点通过 query 参数传递 Token（EventSource 不支持自定义 headers）
    check_token(token)
```

**可能触发场景**：
1. 用户浏览器历史记录中残留含 token 的 URL
2. 服务器访问日志（若有）记录含 token 的 URL
3. 本机恶意进程读取浏览器历史或进程命令行参数

**建议修复方式**：
- token 加过期机制（如 1 小时后刷新）
- SSE 改用短期一次性 token（首次 GET 获取，后续用 Header）
- 或接受当前设计（本机绑定，风险中等）

**是否建议立即修复**：**否（P1）** — 本机绑定限制了利用面；但建议加过期

### 2.6 H6 — `get_custom_danmu_pool_for_store` 缓存失效时主线程读 20000 行

**问题描述**：自定义弹幕库读取函数不分页，单次 `fetchall` 读全表（上限 20000 行）。虽有按 `id(config)` 的缓存（`_custom_pool_text_set`），但写入后 `invalidate_formula_text_cache` 失效，**下次读取在主线程同步加载 20000 行**，可能短暂阻塞 UI。

**影响范围**：主线程响应性；用户编辑弹幕库后的首次读取

**证据位置**：

[app/danmu_pool.py:495-504](../app/danmu_pool.py#L495-L504)：

```python
def get_custom_danmu_pool_for_store(store) -> list[str]:
    if not store._conn_usable():
        return []
    try:
        rows = store.conn.execute(
            "SELECT text FROM custom_danmu_pool_entries ORDER BY id ASC LIMIT 20000"
        ).fetchall()   # ← 主线程同步读 20000 行
    except sqlite3.ProgrammingError:
        return []
    return [str(row[0]).strip() for row in rows if row and row[0] and str(row[0]).strip()]
```

**可能触发场景**：
1. 用户在 Web 控制台编辑公式化弹幕库（写入触发缓存失效）
2. 下次主链路需要补足弹幕时调用 `get_custom_danmu_pool_for_store`
3. 主线程同步读 20000 行 SQLite，WAL 模式下仍可能 50-200ms 阻塞

**建议修复方式**：
- 分页读取（如每批 1000 行，按需加载）
- 或移到 worker 线程预加载
- 或保持缓存策略但优化失效条件（仅在实际变更时失效，而非任何写入）

**是否建议立即修复**：**否（P2）** — 缓存命中时无问题；仅失效时短暂阻塞

## 3. 中低风险问题

### 3.1 资源管理

#### 3.1.1 `_meme_barrage_api_client` quit 未关闭

**证据**：[app/main_meme_mixin.py:40-45](../app/main_meme_mixin.py#L40-L45) 缓存了 `MemeBarrageApiClient` 实例（内部持有 httpx 客户端连接池），但 [app/main_lifecycle_mixin.py:667-759](../app/main_lifecycle_mixin.py#L667-L759) 的 `quit()` 清理了 mic_service / ai_worker / config / pet / web_server，**未见关闭 `_meme_barrage_api_client`**。

**影响**：httpx 客户端持有连接池，进程退出时由 OS 回收，**非严重泄漏但不够干净**。

另外 [app/web_api/meme_barrage.py:160](../app/web_api/meme_barrage.py#L160) 每次调用 `get_tags` 都新建 `MemeBarrageApiClient()` 且不 close，是临时泄漏（依赖 GC）。

#### 3.1.2 `ai_worker_pool`/`meme_ai_pool` quit 未 waitForDone

**证据**：[app/main_lifecycle_mixin.py:687-705](../app/main_lifecycle_mixin.py#L687-L705) 的 `quit()` 等待 `capture_worker_pool` 与全局 pool，但 [app/worker_pools.py:19-44](../app/worker_pools.py#L19-L44) 定义的 `ai_worker_pool()`（maxThreadCount=2）与 `meme_ai_pool()`（maxThreadCount=1）**未被显式 waitForDone**。

**影响**：退出时若有 AI/meme runnable 在跑，`config.close()`（行 741）后它们可能访问已关闭的 SQLite。`ai_worker.close()` 已 `mark_stopping`，但 meme_ai_pool 的 runnable 无 stopping 标志。

### 3.2 主线程阻塞

#### 3.2.1 SQLite 大批量写入持锁

**证据**：[app/config_store.py:283-290](file:///e:/test/danmu/app/config_store.py#L283-L290) 的 `set()` 持 `_write_lock` + `conn.execute` + `commit` 在主线程。WAL + `busy_timeout=5000`（行 112-114）缓解读写并发。`meme_barrage_library_insert_many`（行 844-853）的 `executemany` 也在主线程持锁执行。

**影响**：大批量写入（如烂梗库批量导入）会在主线程持 `_write_lock` 期间阻塞 UI。

#### 3.2.2 WebConsoleBridge.invoke_on_main 串行排队 10s 超时

**证据**：[app/web_console.py:186-231](../app/web_console.py#L186-L231) 所有 Web 写路由经 `invoke_on_main` 串行排队到主线程，`INVOKE_ON_MAIN_TIMEOUT_SEC = 10.0`（行 94）。

**影响**：主线程若繁忙（截图 tick / AI 回复消费），Web 写请求被串行阻塞，多个并发写请求叠加等待。超时返回 504。这是 Qt 单线程约束的必然权衡，但**主线程任一长操作会拖累全部 Web 控制台响应**。

### 3.3 异常处理

#### 3.3.1 56 处 `except Exception`（多数可接受）

**证据**：grep `app/` 命中 56 处 `except Exception:`。典型：

- [app/config_store.py:66](file:///e:/test/danmu/app/config_store.py#L66)（chmod best-effort）— **可接受**
- [app/ai_client.py:416](../app/ai_client.py#L416)（close best-effort）— **可接受**
